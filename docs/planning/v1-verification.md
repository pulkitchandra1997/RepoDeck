Updated: 2026-09-11. V1 is in development, not ready for stable release.

An unsigned Windows development installer is now available for evaluation. It is not a stable v1 release.

Latest packaged increment: Open in terminal is available in the repository inspector, with a persisted Terminal preference. Existing settings default to `system`. Windows presets currently cover system/Windows PowerShell and Command Prompt; macOS system maps to Terminal. The core checks that the target is an existing directory within the workspace and never interpolates its path into shell instructions. Windows uses an absolute system executable, fixed preset flags, a separate working-directory field and a child-only environment via [CreateProcessW](https://learn.microsoft.com/en-us/windows/win32/api/processthreadsapi/nf-processthreadsapi-createprocessw). PowerShell uses [NoProfile/NoExit](https://learn.microsoft.com/en-us/powershell/module/microsoft.powershell.core/about/about_powershell_exe?view=powershell-5.1); Command Prompt disables AutoRun with `/D`. Execution policy is not changed.

All 60 ordinary native and 41 frontend tests passed at implementation time; the 41-test frontend suite passed again during packaging. The installed Windows app now passes both PowerShell and Command Prompt workflows: save the choice, verify it on disk, launch from the repository inspector, read the Express-directory prompt, send a fixed harmless echo command through console input, and observe both the entered command and its output. `scripts/fixtures/terminal-read.rs` attaches only to the newly created child console; the harness terminates that shell afterward. Compile the Windows console fixture with rustc and set `REPODECK_TEST_TERMINAL` to its absolute executable path before `node scripts/verify-native.cjs`; set `REPODECK_TEST_EXE` to exercise an installed build. Custom terminal applications, UNC/long-path behavior, broader command interaction and macOS remain outstanding.

Terminal testing found inherited PSModulePath causing a publisher prompt for the agent runtime's PSReadLine module. The child environment now omits that override without changing machine settings or execution policy. A second issue was redirected handles reaching the new console; direct Windows process creation now disables handle inheritance so the console owns stdin/stdout. The console-reader fixture was corrected to open CONOUT$ rather than its redirected output handle, and it retries attachment while the console starts. One test was started before linking finished and locked the old binary; both failed runs were stopped, the rebuild completed, and the fresh executable passed. These failed attempts are not success evidence.
